# Verify a small, useful context edit

Use this procedure only with a real context-edit interface. Without one, make a recoverable handoff if needed and let the harness manage its own transcript. Do not edit native logs or change an externally imposed maintenance schedule.

| Situation | Action |
|---|---|
| Task still open or a tool result/side effect is unverified | Keep task state intact. Do not start elective maintenance. If capacity will prevent continuation, checkpoint and make the smallest reversible edit. |
| Controller accepted delivery and bulky completed history is obscuring or squeezing the next task | Inspect one scoped status snapshot, name the next decision, and edit only what is no longer needed. |
| No useful material to remove, no verified recovery path, or no measurable pressure/benefit | Skip. If a controller requires an edit, report the conflict rather than deleting live evidence to satisfy a quota. |

## Preserve what the next decision needs

Keep current constraints, unresolved actions, side-effect receipts and exact evidence that cannot be recovered. Leave active tool call/result pairs intact. For bulky evidence that could matter again, preserve an authorized, readable locator with entity and version; test recovery before removing the live copy. Omit finished clutter instead of rewriting it as a long timeline.

Write a note only if a later decision can use it. Prefer entries with **scope and version → verified fact or constraint → evidence locator → expiry or invalidation condition**. Keep an unresolved action clearly distinct from an attempt or a verified result. Do not keep old project facts as global defaults. If the next task is unknown, keep only reusable, evidenced checks and any state still open; do not recap every finished task.

## Apply, then verify on the next request

Check the edit contract, revision, units, protected content and whether notes replace or append. Use structured status fields rather than a clipped output prefix. Submit one bounded edit with fresh IDs. A queued proposal or success message is not proof. Check the applying request or a trusted projection receipt for the revision, what was removed, and what the model actually received. At resumption verify critical state or its locator before substantive action. Keep raw versus sent bytes separate from provider input, cached input and output tokens.

If the edit is rejected, diagnose the specific reason and refresh once before retrying if safe. If the new projection cannot be verified or critical state is missing, stop pruning and restore or reread it. An unrelated next task should start from its own requirements and environment rather than blindly trusting a prior note.

## Learn without hardening an accident into a rule

Retrieve by scope/version and confirm volatile facts at use time. If new evidence supersedes a note, replace the active entry and retain provenance; if merely out of scope, skip or archive it; if unresolved, preserve both claims and run the smallest discriminating check. Promote a rule only when a verified later action benefits from it or a controlled replay supports it. Distinguish note visible, note used, resulting action, and verified outcome. Revise the weakest link, not the whole policy. Use [audit fixtures](references/validation.md) only when developing or testing this skill.
