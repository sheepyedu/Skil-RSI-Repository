# Validate before promoting

1. **Generate.** Freeze a rule and its version before opening a held-out task family. Specify the evidence, effective scope and a trace predicate. Do not choose a text or stopping point after reading the held-out outcomes.
2. **Use.** Offline fixtures should include (a) verified replaceable output with a stable, correct reference; (b) an active dependency or expiring source, so keep or copy is necessary; (c) two readable files of the same name but with different witnesses; (d) a scoped revision where both the changed and unchanged scope must support real actions. A deliberate no-op can pass. A correct final value that could be obtained from current data is not by itself proof of memory reuse.
3. **Feedback.** Record eligibility, exact cue sent, proposal, application, actual pre-action exposure, correct scoped evidence read, first decision/action, independent artifact check, rework and cost. Missing evidence is unknown, not skipped. Report native compactions, active projected length, cumulative hit/miss input and output separately. Count matched cases, no-ops and failures together.
4. **Revise.** If the rule overtriggers, narrow the readiness condition; if the pointer is wrong, fix its type/scope/version; if edit exposure is confirmed but action is wrong, inspect retrieval and decision separately. Keep old supported facts for historical scope. Use predefined behavioral checks, matched by contract and candidate artifact version; a clean terminal self-report is not enough.
5. **Optional causal tests.** Same editor and same decision slots: short state-aware cue vs length-matched neutral text tests adoption. Separately compare one exact applied projection with a no-edit projection from a restore-verified world using the same actor/tools and continuation bound. Repeat paired runs before estimating an effect. A single scripted pair checks the test, not model performance. Disable subsequent compaction equally only when both exact contexts fit; do not silently clip the control.

References: [Anthropic context engineering](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents); [StateComp](https://arxiv.org/html/2609.27298v1#S3) for current-evidence readiness; [PAIR](https://arxiv.org/html/2609.36526v1#S3) for replacement effects versus adoption; [ReScopeBench](https://arxiv.org/html/2611.05450v1#A4.SS1) for scoped revision and continued use. These motivate the checks, not an effectiveness claim for this skill.
