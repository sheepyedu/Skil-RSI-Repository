# Claude Code 原生模式下的工程连续性

1. 先锁定工作范围。确认仓库和工作树、分支与 HEAD、当前需求、允许和禁止修改的路径，以及已有的暂存、未暂存和相关未跟踪内容。保留原有改动。普通 Git diff 为空，不代表没有超范围改动。
2. 把里程碑当作同一工作的不同阶段。确认当前阶段和哪些依赖已经验证，保留生效需求、尚未通过的检查或未证实的假设，以及一项可执行的下一步。不要为了整理上下文新开会话，也不要因此标记阶段完成。
3. 运行时发生压缩或需要恢复同一会话时，以范围内工作区和原始证据为准，不只依赖摘要。能确认时核对会话和工作树身份，比较前后已跟踪和未跟踪状态；在相同状态下检查原有结果，或运行必要的最小检查。需要时才回读原文，发现笔记过时就纠正。
4. 报告完成前，区分验证新功能的由失败变通过（F2P）、验证既有行为不回归的持续通过（P2P），以及正式评测结果。代表性本地检查不得代替正式评测；核对范围时不要漏掉未跟踪内容。检查命令成功、提交或压缩摘要本身都不是正式验收。
5. 约束重试。如果会话或环境身份意外变化、先前操作是否生效不明，或反复没有实质进展，先保留状态并定位阻碍。只有已获授权的协议允许时，才新开会话、重置工作树、扩大范围或重新提交；允许轮换时也要明确标记为新会话。

**证据冲突时：**先核对来源权限和适用范围，不以最新记录自动覆盖旧记录。只更新被替代的事实，保留仍有效的范围。不要为了修复上下文直接改宿主会话文件、权限配置或评分器；走已授权的运行时入口。

本技能不提供实时上下文编辑能力，也不是触发手动压缩的理由。遵循宿主默认机制和操作者的明确要求。排查恢复失败、回归或效果归因时，读[验证说明](references/validation.md)。
